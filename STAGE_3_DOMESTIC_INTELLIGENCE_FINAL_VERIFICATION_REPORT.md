## 1. EXACT RUNTIME ROOT CAUSE

### 1.1 Summary of the Defect
The runtime exception `TypeError: a[d] is not a function` reported at browser URL `http://localhost:3001/domestic` was **not** caused by application syntax errors, component hierarchy flaws, or unhandled React exceptions. It was the direct result of **Webpack development bundle cache corruption and orphaned asset desynchronization**.

### 1.2 Chronological Forensic Reconstruction
1. **Initial Process State:** At **14:40:56**, the Next.js development server process (PID `10332`) was started via `npx next dev -p 3001`. The Webpack development compiler generated in-memory and disk-based unhashed chunks under `.next/static/chunks/` (specifically `app/domestic/page.js`, `main-app.js`, `app-pages-internals.js`, and `app/not-found.js`).
2. **Interleaved Production Build Execution:** At **18:25**, during the Stage 3 completion gate, `npm run build` was invoked. In Next.js 15, `next build` unconditionally purges and recreates the `.next/` directory, outputting production-hashed chunks (e.g., `main-app-8beccbb40c472b58.js`, `page-c7c3565db0da749e.js`).
3. **Chunk Orphanage on the Dev Server:** While the `.next/` directory on disk was completely overwritten with production artifacts, the development server process (PID `10332`) remained alive in memory. When a client requested `http://localhost:3001/domestic`, the server rendered SSR HTML referencing the development script manifests:
   ```html
   <script src="/_next/static/chunks/main-app.js?v=1795009855915" async=""></script>
   <script src="/_next/static/chunks/app-pages-internals.js" async=""></script>
   <script src="/_next/static/chunks/app/domestic/page.js" async=""></script>
   ```
4. **HTTP 404 Chunk Failures:** When the browser subsequently requested these script URLs from `http://localhost:3001`, the server attempted to read them from disk, could not locate the deleted development chunks, and returned **HTTP 404 HTML error pages**.
5. **The Webpack Runtime Failure (`a[d] is not a function`):**
   In the Webpack client runtime (`webpack.js`), chunk loading manages an array of installed chunks (`installedChunks` / `a`). When a chunk file loads, it registers its module factory functions. Because the script request failed (returned HTML 404), the module callback was never registered:
   ```javascript
   // Webpack chunk installer invocation:
   installedChunks[chunkId][0](); // In minified bundle: a[d]()
   ```
   Evaluating `a[d]()` where `a[d]` is `undefined` threw `TypeError: a[d] is not a function`. Next.js caught this in its client-side error boundary, spawning the 14-frame runtime error overlay.

### 1.3 Secondary API Serialization Discrepancy
Forensic inspection of the network layer and TypeScript client contracts revealed an API serialization defect:
- In `backend/app/schemas/domestic_api.py`, `MatchListResponse` defines `total_matches: int`.
- In `frontend/src/lib/api.ts`, `fetchSeasonMatches` expected `{ total: number }`.
- In `frontend/src/app/domestic/page.tsx`, `matchTotal` evaluated to `undefined`, causing the match count badge to display `(0)`.
